A user sends a message to our chatbot: *"gracias"*.

Seventeen seconds later, the chatbot replies: *"de nada, ¿hay algo más en lo que pueda ayudarte?"*

Three things happened during those seventeen seconds. None of them needed to.

The user asked a question that any junior model could answer in a sentence. We sent it to the most expensive, slowest, most thoughtful model in the stack — the same one that takes its time reasoning through nutrition trade-offs and parsing weeks of training history. The model thought carefully about *"gracias"*, decided it was a polite acknowledgment, and produced a polite acknowledgment in return.

This is a post about the routing layer we built so that question — and every question shaped like it — stopped passing through the wrong door.

<Callout title="What this post is" type="info">
A story about a chatbot that ran every message through the same slow reasoning model — including *"hi"* and *"thanks"* — because that's what shipped first and *"it worked"*. About the small router we added that decides which model each message deserves, and the response-time gains that came out of it. About a reframe that turns out to apply to a lot more than chatbots.

The technical detail is the texture, not the point.
</Callout>

## What we'd shipped first

The first version of the chatbot did the obvious thing. One model. Every message — from *"gracias"* to *"explain why my deadlift programming has plateaued for three weeks"* — went to the same reasoning model, with the same time budget, with the same tool-loop budget, with the same instructions in the system prompt. Whatever the question, the same engine processed it.

That model is excellent. It is also slow and expensive. It has to be — that's what reasoning costs. The reasoning model takes ten to twenty seconds to produce a thoughtful answer when the question deserves it. When the question doesn't deserve it, the model still takes ten to twenty seconds. It does not know what the question deserves. It just answers.

For the first month of beta this was fine, in the way that "we have one MVP path that covers every case" is always fine for the first month of a beta. The chatbot worked. Users got their answers. Nobody was sending us complaints. The numbers we measured were the numbers we knew how to measure: did the answer fire, did the tool calls land, did the user thumb-up the response.

What we weren't measuring, until we started measuring it, was how it *felt* to type *"hi"* and wait. Seventeen seconds is a long time to wait for a model to acknowledge you. It is also five seconds longer than the system prompt's content takes to be transmitted across the network. So the model wasn't even thinking for most of it — it was just being patient about its own thoughtfulness.

## The reframe — one sentence

We had a baseline of around 2,700 messages across two weeks. The median time-to-first-response on what we'd labeled "smalltalk" — *gracias*, *hola*, *ok*, *vale* — was about seventeen seconds. The median on "definition-style" questions (*"what is RPE?"*, *"what is hypertrophy?"*) was about sixteen seconds. The median on actual analytical questions (*"how was my last workout?"*, *"give me feedback on my routine"*) was about thirty-eight seconds.

The pattern in the numbers is obvious once you let it sit for a minute:

<Callout title="The reframe" type="info">
The most expensive model in the stack was answering *every* question at roughly the same speed — because the work it does is invariant to the question. *"Gracias"* and *"give me feedback on my routine"* took the same kind of thinking, the same tool budget, the same wind-up.

That meant we weren't getting slower on the hard questions. We were getting *the same speed* on the easy ones.
</Callout>

The fix wasn't to make the reasoning model faster. The fix was to stop asking the reasoning model questions it had no business being asked.

## The first bump — *"smalltalk just goes to a small model, easy"*

The first attempt was the obvious one. We added a small *Phase 1* shortcut at the top of the pipeline: if the message matches a tight set of patterns — bare greetings, bare thank-yous, bare acknowledgments — route it directly to a smaller, faster model and skip the entire tool-loop. Don't even build the system prompt context. Don't even let the reasoning model see the message.

This is one of those changes that feels like it should obviously work and obviously will keep working. Smalltalk is bounded. There are maybe twenty phrasings that count as *"hi"*. Match those, shortcut them, move on.

In practice the cliff is sharper than you'd expect. The router has to *recognize* smalltalk reliably enough that it doesn't accidentally shortcut a real question. *"Hola"* on its own is smalltalk. *"Hola, ¿cómo afecta una carga del 70% al volumen efectivo de pierna?"* is absolutely not smalltalk. Substring matching fails immediately. So even the simplest shortcut isn't a regex — it's already a small model deciding which bucket the message lands in.

Phase 1 was a strict, conservative version of that bucket-decider. It only triggered on the cleanest cases. Anything that looked even slightly like a real question fell through to the original expensive path. Median time-to-first-response on smalltalk dropped from around seventeen seconds to around four. We shipped it the same afternoon.

What it did *not* do was solve the cases that mattered more — the questions that aren't smalltalk and aren't analytical either. *"What is RPE?"* doesn't need reasoning. It needs a one-paragraph definition. It still went to the slow path.

## The second bump — classifying everything, not just smalltalk

Phase 1 made it clear that the right shape was *every message starts with a small, fast classification step*, not just the smalltalk cases. So Phase 2 was the same idea, generalized.

The new router is the same small fast model. Its only job is to look at the message and decide which of a small set of *intent classes* it belongs to. The classes are deliberately coarse — a handful, not dozens. Each class has a route: *answer it yourself*, *send it to the reasoning model with a pre-planned directive about what to do*, *send it to the reasoning model with no pre-planning because it really is open-ended*.

For the in-between classes — *"what is RPE?"*, *"what is hypertrophy?"* — the router can usually answer the question on its own. These are bounded definitional questions that any model trained on the public internet has a good answer for. The reasoning model is overkill for them and adds nothing the user notices. Median time-to-first-response on this class dropped from around sixteen seconds to around four.

For the analytical class — the questions that genuinely need the reasoning model + the user's data — the router still routes there. But it does one more thing on the way: it writes a short *directive* for the reasoning model. *"User is asking about their squat 1RM history. Last six weeks of data should be sufficient. Focus on weekly load progression."* The reasoning model gets to skip the part where it figures out what tool to call first; the router has already told it. That alone shaved several seconds off the analytical path, because the reasoning model converges in fewer tool-loops.

This isn't an optimization. It's a re-allocation. The router does the work the reasoning model used to do for free.

## The third bump — the crisis with max_tokens

Phase 2 shipped. It mostly worked. The smalltalk class held its four-second median. The definition class came in around five. The analytical class came in around fifteen — slower than smalltalk, faster than the original baseline. We started writing the recap.

Then a colleague pinged me to say the analytical class was sometimes returning *empty responses*. Not slow responses. Empty.

I dug in. The reasoning model was being called. The reasoning model was finishing. The reasoning model was returning a payload with `finish_reason: length` and zero content tokens. We were asking for an answer, and the model was telling us *"I tried, but I ran out of room before I could say anything."*

The bug was a single number. The reasoning model needs headroom to *think* before it produces output. Its reasoning tokens count against the same budget as its output tokens. We had set the max-tokens cap at 256, because that was enough for the original short answers the router-less version produced. After Phase 2 the reasoning model was sometimes spending 256 tokens just *thinking through* the directive the router had given it — and then it had zero tokens left to actually write the answer. The model was hitting the cap during the silent reasoning phase. The user got nothing back.

We bumped the cap to 1024 and added a hard 12-second timeout. Empty responses dropped to zero. The 12-second timeout was the more interesting choice — it forced us to admit that the reasoning model occasionally just doesn't return, and that the right answer in those cases is to fall back gracefully rather than to make the user wait indefinitely.

I think about this bump the most. It's not a story about a clever fix. It's a story about a number that worked for one version of the system and silently became wrong when the system changed shape around it. There was no test that caught it because the test was checking *"does the response fire"*, not *"does the response contain anything"*. The cap was load-bearing in a way the original author of that line never thought to write down.

## The fourth bump — the data was already in the room

There's a particular shape of question users ask a fitness chatbot a lot. *"What's my current streak?"* *"How many sessions did I do last week?"* *"What was my heaviest lift this month?"* These look like analytical questions, but they're not. They're lookups. The answer is one number, retrieved from one place, with no reasoning required.

In the original pipeline these still went to the reasoning model. The reasoning model would call a tool to fetch the user's training history, get back a payload of data, and then *think about it* for several seconds before reporting back a single number that was already in the payload.

After Phase 2 we added one more thing: a *sufficiency check*. After the first tool call returns, the router glances at the result and asks: *"is this enough to answer the question directly?"* If yes, the loop ends — the router writes the answer from the data and returns. The reasoning model is never woken up.

This is the cheapest optimization in the post. It's a single conditional on a path that was already going to run. It cut the lookup-question median from around twenty-one seconds to around nine. The reasoning model was being summoned to thoughtfully tell users a number we'd literally just handed it.

## The architecture, in one picture

By the time all four bumps were in, the shape was different enough that it's worth seeing:

The shape of the picture is the shape of the fix. The big reasoning model used to be the only door. Now it is *one door at the end of a corridor*, and most users never reach it.

## The numbers (at the end, where they belong)

Same beta cohort, same two-week measurement window before and after. Sample baseline: ~2,700 messages.

| Question class | Before (median) | After (median) | Δ |
| --- | --- | --- | --- |
| Smalltalk (*gracias*, *hola*, *ok*) | ~17 s | ~4 s | **−77 %** |
| Definition-style (*what is RPE?*) | ~16 s | ~4 s | **−70 %** |
| Lookup-style (*what's my streak?*) | ~21 s | ~9 s | **−57 %** |
| Analytical (*feedback on my routine*) | ~38 s | ~15 s | **−60 %** |

The number we expected to move was the smalltalk one. The numbers that surprised us were the lookup and analytical ones — both got faster *as a side effect* of the router pre-planning what to do.

We didn't make any single model faster. We just made sure the right model was the one being asked.

## The deeper why — model choice is a contract, not an optimization

When most engineers talk about "AI cost" or "AI latency," they tend to talk about it as a knob — the model is fixed, the costs are what they are, the latency is what it is, the only lever is asking the model less often. That framing leaves a lot of work on the table.

The reframe that actually moves the numbers is to stop thinking about *one* model and to start thinking about a *stack* of them. The stack has a small, fast, cheap model at the top that decides which other model — or no model at all — gets to do the actual work. The top model is the routing layer. Its job is to be the smallest entity that can correctly decide what the question deserves.

<Callout title="The contract a router enforces">
Every message deserves the *smallest* model that can answer it correctly. The router doesn't try to answer the question. It only decides which engine should.
</Callout>

This sounds like a small idea. It is not. It changes the cost profile of the entire product. Most user questions, in any conversational system, are not the questions the system was designed to answer well. They're greetings, acknowledgments, definitional asides, lookups. If those questions never reach the expensive model, the expensive model only has to be good at the small fraction of questions that genuinely deserve it. The economics flip from *"we pay for thoughtfulness on every message"* to *"we pay for thoughtfulness on every message that thoughtfulness improves"*.

The same shape shows up in places that have nothing to do with AI. Cache layers in front of databases. Approval thresholds in expense reports. Triage steps before specialists in hospitals. Whenever there's an expensive resource that doesn't need to handle every request, somebody eventually puts a cheap classifier in front of it. The classifier is the architecture.

## What I'd want you to take from this — even if you don't write code

    A max-tokens cap of 256 was correct for the original system and silently wrong for the routed one. It would have shipped. Every system has these — constants that were load-bearing in a way nobody wrote down. The fix is to make the constants themselves visible, not to never set them.
